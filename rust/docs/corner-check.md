# 테두리 이음매 검사

## 수정과 재현

- 창 원점은 물리 픽셀로 반올림했지만 렌더 원점은 원래 pt 값을 사용했다. 1366×768, 1.5배, 굵기 3.5, 반지름 40의 닫힌 경로에서는 오른쪽 창의 위상이 -0.125px 어긋났고, 기존 합성과 전체 렌더가 372픽셀에서 달랐다. 최대 채널 차는 52/255였다.
- 2pt 겹침에서 반투명 선을 중복 합성했다. 1512×982, 1.25배, 굵기 3.5의 기본 상단선에서는 52픽셀, 최대 61/255 차이가 났다. 왼쪽 이음매 x=37..39px, 오른쪽 이음매 x=1851..1853px와 오른쪽 끝 캡에서 차이가 났다.
- 노치를 원굵기로 고정한 가우시안 근사 평활 결과와 바깥 슬라이스 사이에 원굵기의 최대 25.3019% 차이가 있었다. 3회 상자 블러를 유지하고, 노치까지의 원형 거리에 따라 바깥 램프를 블러 반경의 1/4(최소 3슬라이스) 범위에서 smoothstep으로 고정 굵기에 연결했다. 같은 시험에서 노치 경계 차이는 0.4240%, 일반 슬라이스 차이는 최대 1.4976%가 됐다. 노치 자체의 굵기는 유지한다.
- 옆 Dock과 고정 메뉴바를 함께 처리하는 창 레이아웃 조건을 장면 생성 조건과 일치시켰다. Dock이 꺼진 상태의 방향 변환에서도 내부 경계가 누락되지 않는다.

`border::strip_layout`이 방향 변환 뒤 내부 경계를 반올림한다. 화면 바깥 끝은 전체 렌더의 올림 크기에 맞춘다. OS 창 프레임은 같은 경계의 차이로 크기를 정한다. 전체 화면을 한 번 렌더한 뒤 `crop_strip`으로 겹치지 않는 영역을 복사하므로 창마다 원점, 곡선 평탄화, 안티앨리어싱이 달라질 수 없다. 호버 강조도 같은 방식이다.

임시 전체 버퍼는 2176×1360, 2배에서 약 45MiB다. 다시 그리는 동안만 보유하며, 각 띠의 창 이미지는 기존처럼 따로 전달한다.

## 회귀 시험

```sh
export PATH="/opt/homebrew/opt/rustup/bin:$HOME/.cargo/bin:$PATH"
cd rust
CORNER_EXHAUSTIVE=1 cargo test --release -p um-render --test border_seams -- --nocapture
CORNER_DUMP=1 cargo test -p um-app overlay::tests -- --nocapture
bash tools/check.sh
cargo clippy -p um-app --all-targets --features store -- -D warnings
```

- 픽셀 비교: 반지름 0/9/22/40, 노치 2가지, 메뉴바·Dock 각각 2가지, 방향 4가지, 겹침 분할 2가지, 세부 항목 겹침 2가지, 굵기 2/3.5/6/15, 배율 1/1.25/1.5/2, 화면 2176×1360/1512×982/1366×768/1367×769의 32,768개 조합이다. 메뉴바 반지름은 본문 값의 0.75배, Dock은 0.5배로 달리 설정한다. 세 AI는 서로 다른 구역 둘레를 공유하여 레인·노드 분할과 굵기 전환을 실제로 발생시킨다. 기본 실행은 모든 축의 값을 포함하는 128개 표본, 환경변수 지정 시 전수 검사다. 허용 오차 없이 premultiplied RGBA가 완전히 같아야 한다.
- 경로 검사: 세 구역 고리의 G0와 닫힘, 직선·곡선 및 분할된 곡선 사이 G1, 유효한 단일·두 구간 경로, 정·역방향 캡, 옆 Dock 접합을 확인한다. 영길이 요소와 의도된 직각의 직선 접합은 G1 대상에서 제외한다.
- 스쿱 반환: 반대 방향 hCaps가 같은 선을 180도로 되짚던 곳은 반환점 앞뒤를 최대 0.25pt씩 잘라 짧은 3차곡선으로 연결한다. 두 접선의 진행 방향까지 일치시키며, 고리 시작점에 걸린 반환도 처리한다. 스쿱을 G1의 예외로 허용하지 않는다. 영길이 요소를 제거한 뒤 연결부를 검사한다.
- 굵기 검사: 스팬 경계 누락·비정상 굵기, 일반 전환의 큰 차이, 노치 고정 경계의 차이를 검사한다. 기존 6pt 슬라이스 표현은 유지하므로 연속 함수로 저장되는 것은 아니다.
- OS 프레임 검사: 분수 배율과 음수 다중 화면 원점에서 인접 창이 같은 경계를 공유하고 크기가 정수 물리 픽셀이 되는지 확인한다.
- Swift PNG와 허용 기준은 변경하지 않는다. `border_ref`의 기존 의도된 차이 `subitems_two_ais` 예외도 그대로다.

확대 이미지는 `target/corner-check/curve-before-right-8x.png`, `curve-after-right-8x.png`에 저장한다. 기본 이음매 재현의 전체 이미지와 좌우 8배 확대도 같은 폴더에 저장한다.

## 확인 결과

- 최종 release 전수 검사: 32,768개 조합 모두 채널 차 0, 경로·굵기 검사를 포함한 5개 시험 통과(393.66초).

- macOS 워크스페이스 테스트, Swift 기준 이미지 비교, 워크스페이스 clippy, Store 기능 clippy 통과.
- 플랫폼 크레이트는 `cargo clippy -p um-platform --all-targets --target <대상> -- -D warnings`로 Windows x64와 ARM64 모두 통과.
- `bash tools/check.sh`는 macOS 단계를 통과한 뒤 Windows 단계의 cargo-xwin 캐시 링크 교체에서 실패한다. `/Users/wwhalefe/Library/Caches/cargo-xwin/clang-cl` 삭제 권한 오류다. ARM64 전체 검사도 동일한 오류를 확인했다. 저장소 밖 파일이나 `XWIN_CACHE_DIR`은 변경하지 않았다. 전체 스크립트 통과로 보고할 수 없는 환경 제약이다.
- Swift 기준 PNG와 비교 임계값은 모두 원래 값이다. 노치 평활 보정의 영향은 `split2_on_notch`(mean_all 0.0398, mean_ink 1.397, 차>32 251픽셀), `split3_on_notch`(0.0932, 1.589, 396픽셀)에 남지만 기존 허용 기준을 통과한다. 스쿱 보정도 기존 기준을 통과한다.

변경 파일: `um-app/src/overlay.rs`는 공통 버퍼 렌더·분할 및 이전 결함 재현, `um-platform/src/display.rs`는 프레임 경계 반올림과 다중 화면 검사, `um-render/src/border/strips.rs`는 공유 레이아웃·픽셀 추출, `shape.rs`는 스쿱 반환 G1 보정, `spans.rs`는 노치 경계 평활, `mod.rs`는 보정 연결과 API 내보내기, `draw.rs`는 띠 렌더 사용 설명, `tests/border_seams.rs`는 픽셀·경로·굵기 회귀 검사다.
